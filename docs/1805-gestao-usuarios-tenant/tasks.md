Para isolar e verificar o código desta tarefa, a query REST `tenant_members` do `useAuth` e as rotas `app/api/tenants/[id]/members*` foram mockadas via interceptação de rede (Playwright `page.route`); com isso, confirmado visualmente: aba "Equipe" visível para `owner`/`admin` e ausente para `gestor`/`operador`; listagem renderiza nome/e-mail/papel+descrição de uma linha/toggle de IA/status; convite abre modal com descrições de papel inline e atualiza ao trocar o select; edição inline de papel/toggle funciona e persiste (via mock); reenvio de convite pendente mostra confirmação sem duplicar linha; remoção de membro ativo exige confirmação prévia, revogação de convite pendente usa rótulo distinto; linha do owner não renderiza nenhum controle de editar/remover; erros 409/502 do convite aparecem com o texto específico do backend (não genérico). Também verificado contra o backend real (sem mock): com owner autenticado de verdade, a aba aparece e o painel mostra corretamente o erro real retornado pela API (`"Tenant ativo não encontrado."`, 404) em vez de uma falha silenciosa — evidência de que o tratamento de erro do painel é fiel ao contrato da API mesmo no estado pré-migração. Testado em 1440px e 390px (mobile) — a tabela usa `overflow-x-auto`; durante a verificação a coluna de Ações ficava fora da área visível mesmo em desktop por causa do container estreito do layout de abas (sidebar 3/12 + `max-w-5xl`), then corrigido reduzindo `min-w` da tabela, truncando a descrição do papel para uma linha na lista (mantendo a descrição completa no convite/edição, conforme ADR-001) e trocando os botões de ação para ícone com `title`/`aria-label` (padrão já usado em `components/clients/client-actions.tsx`).
