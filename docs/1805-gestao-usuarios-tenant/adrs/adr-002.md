# ADR-002: Mutações de gestão de equipe passam pelo client admin de service role

## Status

Aceito

## Data

2026-08-12

## Contexto

A RLS de `tenant_members` hoje é inconsistente entre as operações: `tenant_members_insert` e `tenant_members_delete` (do `supabase_tenant_model.sql`) só permitem que o `owner_user_id` da linha mude, enquanto `tenant_members_update` (do `supabase_roles_permissions.sql`, adicionado para a tarefa 17 do roadmap) já permite `owner` OU `admin` via uma subconsulta na própria linha de associação do ator. `tenant_members_select` permite que qualquer membro ativo do tenant leia a lista completa de membros.

O PRD exige que `owner` E `admin` possam convidar, editar papéis/permissões, reenviar/revogar convites e remover membros de equipe. Depender da RLS diretamente exigiria alinhar `insert`/`delete` com a política `update` já inconsistente, e ainda precisaria de uma forma de criar uma linha para um usuário que ainda não existe em `auth.users` (o convidante não pode inserir uma linha `tenant_members` referenciando um usuário que não existe até que a API de convite do Supabase Auth o crie).

O projeto já tem um padrão estabelecido exatamente para essa situação: `app/api/admin/users/route.ts` usa `getSupabaseAdmin()` (service role, ignora a RLS) com autorização aplicada inteiramente no route handler, porque a mutação precisa de privilégios de admin de `auth.users` que nenhuma política RLS de papel anon/authenticated pode conceder.

## Decisão

Todas as rotas de API de gestão de equipe (`app/api/tenants/[id]/members/*`) usam o client de service role (`getSupabaseAdmin()`) para toda mutação (convidar, alterar papel/permissão, reenviar, revogar, remover). A autorização é aplicada inteiramente no route handler via `requireRole(req, 'admin', tenantId)` (owner e admin passam; a própria linha do `owner` é adicionalmente protegida por uma verificação explícita em nível de código, não pela RLS). Toda consulta filtra manualmente `.eq('tenant_id', ctx.tenantId)` conforme a convenção existente de client admin do projeto (ver CLAUDE.md, "Admin (service role) client").

As políticas RLS de `tenant_members` ficam inalteradas. Elas permanecem como rede de segurança de defesa em profundidade para qualquer caminho de código futuro que consulte `tenant_members` com o client não admin, não como a fronteira primária de autorização desta funcionalidade.

O endpoint de leitura (`GET /api/tenants/[id]/members`, listagem da equipe) usa o client normal com escopo de tenant, contando com a política `tenant_members_select` existente (qualquer membro ativo pode ver a lista da equipe) — nenhum client admin é necessário para leituras.

## Alternativas Consideradas

### Alternativa 1: Alinhar as políticas RLS (insert/delete correspondem à verificação owner+admin do update)

- **Descrição**: Escrever uma migração estendendo `tenant_members_insert`/`tenant_members_delete` para aceitar `role IN ('owner','admin')` na própria associação do ator, espelhando `tenant_members_update`.
- **Prós**: A RLS se torna a fronteira real de autorização, consistente com o padrão geral do projeto para tabelas com escopo de tenant; protege contra mau uso direto do client mesmo de código novo que esqueça de verificar o papel.
- **Contras**: Ainda não resolve convidar um usuário que não existe em `auth.users` ainda — o passo de convite é inevitavelmente uma operação de client admin (`auth.admin.inviteUserByEmail`) independentemente de como a RLS de `tenant_members` seja escrita, já que a linha de associação real de um convite pendente é criada pelo trigger `handle_new_user()` (ver ADR-003), não por um insert direto do client. Alinhar a RLS ajudaria apenas as rotas de mudança de papel e remoção, não o convite em si — então a funcionalidade acabaria usando tanto caminhos autorizados por RLS quanto caminhos autorizados por client admin para ações intimamente relacionadas, o que é mais inconsistente, não menos.
- **Por que rejeitada**: Não resolve completamente o problema que pretendia resolver, e produz dois modelos de autorização dentro da mesma funcionalidade.

## Consequências

### Positivas

- Um único modelo de autorização para toda mutação de gestão de equipe, correspondendo ao precedente existente de `admin/users` — revisores e mantenedores futuros só precisam aprender um padrão.
- Nenhum risco de migração de RLS em `tenant_members` para esta funcionalidade; as políticas existentes (já inconsistentes) ficam intocadas em vez de serem estendidas ainda mais.

### Negativas

- As políticas de insert/delete da RLS de `tenant_members` permanecem mais restritas (apenas owner) do que a camada de aplicação permite (owner+admin) — uma inconsistência latente, mas que precede esta funcionalidade e está explicitamente fora de escopo corrigir aqui.
- Toda rota nova deve lembrar de filtrar `.eq('tenant_id', ...)` manualmente já que a RLS não oferece rede de segurança ao usar o client admin — risco padrão já aceito no projeto inteiro para código de client admin.

### Riscos

- Uma futura escrita direta (sem client admin) em `tenant_members` ainda poderia ter sucesso sob as políticas de insert/delete apenas-owner e contornar completamente a verificação de papel do admin — mitigado mantendo todas as escritas de gestão de equipe centralizadas no conjunto pequeno de rotas sob `app/api/tenants/[id]/members/*`.

## Notas de Implementação

- `requireRole(req, 'admin', tenantId)` protege a entrada de toda rota de mutação; um `if (targetMember.role === 'owner') return 403` explícito protege a mudança de papel/remoção contra jamais tocar a linha do owner, independente da camada de RLS.
