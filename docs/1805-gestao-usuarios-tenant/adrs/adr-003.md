# ADR-003: Convite via metadados do Supabase Auth, tenant_members como armazenamento único do estado do convite

## Status

Aceito

## Data

2026-08-12

## Contexto

Não existe fluxo de convite hoje. Todo INSERT em `auth.users` dispara incondicionalmente `handle_new_user()` (`supabase_tenant_model.sql:892-918`), que cria um tenant novo e uma associação `owner` para aquele usuário. `inviteUserByEmail` (API Admin do Supabase Auth) também insere uma linha em `auth.users` (não confirmada, `email_confirmed_at IS NULL`) no momento em que o convite é enviado — antes de a pessoa convidada definir a senha. Esse INSERT dispara o mesmo trigger, então um `handle_new_user()` não modificado daria a cada usuário convidado seu próprio tenant separado em vez de juntá-lo ao tenant convidante, entrando em conflito direto com o propósito da funcionalidade.

Nenhum código do projeto depende de metadados personalizados de `auth.users` hoje (`handle_new_user()` só lê `name`), então introduzir metadados específicos de convite é uma extensão limpa, não uma mudança em um contrato existente.

## Decisão

**Entrega do convite**: a rota de convite chama `supabaseAdmin.auth.admin.inviteUserByEmail(email, { data: { invited_tenant_id, invited_role, invited_can_configure_ai } })`. Isso depende do SMTP estar configurado no painel do projeto Supabase (fora deste codebase); se a chamada falhar porque a entrega de e-mail não está configurada, a rota retorna um erro claro em vez de um 500 genérico.

**Trigger ciente de convites**: `handle_new_user()` é modificado para fazer um branch sobre `NEW.raw_user_meta_data ->> 'invited_tenant_id'`. Quando presente (e `invited_role` é um dos quatro papéis válidos), o trigger pula o caminho de auto-cadastro por completo e em vez disso:
1. Insere diretamente em `tenant_members` com `tenant_id = invited_tenant_id`, `role = invited_role`, `status = 'pending'`, `can_configure_ai = invited_can_configure_ai`.
2. Insere em `profiles` com `tenant_id = invited_tenant_id` (não um tenant recém-criado).

Nenhum tenant novo ou associação `owner` é criado para um usuário convidado. Quando os metadados estão ausentes, o caminho de auto-cadastro existente roda inalterado.

**O estado do convite fica inteiramente em `tenant_members.status`** (`pending` → `active`), sem tabela separada `tenant_invitations`. Um segundo trigger novo (`on_auth_user_confirmed`, `AFTER UPDATE ON auth.users`) muda `tenant_members.status` de `pending` para `active` quando `email_confirmed_at` transiciona de `NULL` para não-`NULL` (ou seja, o usuário convidado terminou de definir a senha). Isso não exige polling na camada de aplicação nem rota de callback — o próprio fluxo de confirmação do Supabase dirige a transição de estado.

**Reenviar** re-invoca `inviteUserByEmail` para o mesmo e-mail (ainda não confirmado), que o Supabase reenvia sem criar uma linha `auth.users` duplicada. **Revogar** um convite pendente exclui a linha `tenant_members` e chama `supabaseAdmin.auth.admin.deleteUser(userId)` para liberar o e-mail para um convite futuro (uma linha `auth.users` órfã não confirmada bloquearia permanentemente o reconvite daquele endereço).

**Tratamento de convite duplicado**: se `inviteUserByEmail` falhar porque o e-mail já está registrado (usuário existente, neste tenant ou em outro), a rota retorna 409 com uma mensagem clara em vez de reatribuir silenciosamente o tenant daquela pessoa.

## Alternativas Consideradas

### Alternativa 1: Tabela separada `tenant_invitations` com token/expiração próprios

- **Descrição**: Desacoplar o estado do convite de `tenant_members` por completo — armazenar `email`, `tenant_id`, `role`, `can_configure_ai`, um token e `expires_at` em uma nova tabela; criar a linha `tenant_members` apenas quando o convite for aceito.
- **Prós**: Ciclo de vida de convite explícito (expiração, rotação de token) independente de a pessoa já ter uma linha `auth.users`; sem necessidade de tratar `handle_new_user()` como caso especial.
- **Contras**: Duplica estado que `auth.users` (`invited_at`, `email_confirmed_at`) e a expiração do link de convite do próprio Supabase já controlam; precisa de políticas RLS próprias e de um passo de reconciliação para criar a linha `tenant_members` na aceitação; duas fontes de verdade para "essa pessoa está na equipe" durante a janela de pendência.
- **Por que rejeitada**: `inviteUserByEmail` já cria a linha `auth.users` imediatamente, então uma linha `tenant_members` pendente pode existir desde o mesmo momento — sem lacuna a preencher com uma segunda tabela. Rejeitada por YAGNI; revisitada apenas se semânticas de expiração/token de convite além do que o Supabase Auth oferece se tornarem um requisito real.

### Alternativa 2: Deixar o trigger de cadastro intocado; reconciliar a atribuição de tenant após o primeiro login

- **Descrição**: Deixar `handle_new_user()` continuar criando um tenant autônomo + associação owner para toda linha `auth.users`, incluindo convidadas; uma rota de callback pós-login detecta os metadados de convite e exclui o tenant/associação autônomos, inserindo os corretos em seu lugar.
- **Prós**: Zero mudanças no trigger existente, já funcional.
- **Contras**: Cria um estado inconsistente real (embora breve) — um usuário convidado chega a possuir um tenant fantasma antes da limpeza; a rota de limpeza precisa lidar com falha parcial (tenant criado, rota de limpeza nunca chamada) de forma confiável, o que é estritamente mais superfície de falha do que um único branch condicional no trigger.
- **Por que rejeitada**: Troca uma mudança pequena e bem contida no trigger por um problema maior e com estado de limpeza.

## Consequências

### Positivas

- Nenhuma tabela nova, nenhuma lógica de token/expiração a construir ou proteger — reutiliza o ciclo de vida próprio de convite/confirmação de `auth.users` e a coluna `tenant_members.status` existente.
- A aceitação do convite não exige nenhuma rota nova na aplicação — a transição de estado é dirigida inteiramente pelo fluxo de definição de senha/confirmação do Supabase Auth.

### Negativas

- Adiciona um segundo trigger em `auth.users`, aumentando a superfície que precisa ser entendida ao depurar problemas de cadastro/auth.
- Amarra a correção desta funcionalidade ao comportamento de propagação de metadados do Supabase Auth no `inviteUserByEmail`, uma dependência externa na qual este codebase não confia em nenhum outro lugar hoje.

### Riscos

- Se o SMTP não estiver configurado no projeto Supabase, `inviteUserByEmail` falha no envio — a rota de convite deve evidenciar isso claramente (conforme as Restrições Técnicas do PRD) já que o codebase não tem visibilidade nem controle sobre essa configuração.
- `handle_new_user()` roda como `SECURITY DEFINER`; o novo branch deve validar `invited_role` contra a mesma allow-list da camada de aplicação para que um payload de metadados malformado ou falsificado (não possível via API Admin, mas que vale proteger defensivamente) não possa inserir um papel inválido.
