# ADR-002: Route group `(app)` como ponto único do shell sidebar

## Status

Accepted

## Data

2026-08-08

## Contexto

O PRD (ADR-001) define sidebar persistente em todas as páginas autenticadas, mas hoje cada `page.tsx` renderiza `<Header />` individualmente (~11 arquivos). Para ter um único ponto que monta `SidebarProvider` + `AppSidebar` + `Header` + conteúdo, e que persista o estado do layout entre navegações, é necessário um layout compartilhado no App Router. Sem um route group, seria preciso refatorar cada página manualmente ou repetir o provider em cada uma.

## Decisão

Criar o route group `app/(dashboard)/` com um `layout.tsx` que monta o shell:

- `SidebarProvider` (no nível do layout do grupo) — estado expandido/colapsado em **React context em memória** (ADR-001: sem localStorage), persiste entre páginas do grupo.
- `AppSidebar` (config-driven) + `Header` slim + `SidebarInset` com o `{children}`.
- Mover todas as páginas autenticadas para `app/(dashboard)/` (URLs inalteradas, pois route groups não afetam o path; middleware de sessão continua válido).

O `RootLayout` (`app/layout.tsx`) preserva o `AuthGuard` e o `HelpChat`.

## Alternativas Consideradas

### Alternativa 1: Provider no RootLayout

- **Descrição**: Colocar o `SidebarProvider` em `app/layout.tsx` e o `AppSidebar` global já envolto.
- **Prós**: Não move arquivos.
- **Contras**: Envolveria também `/login` (página pública) e as rotas `/api`, que não devem ter sidebar; exige condicional por pathname ou separação extra.
- **Por que foi rejeitada**: polui o root e mistura página pública com autenticada.

### Alternativa 2: Refatorar cada `page.tsx`

- **Descrição**: Envolver o conteúdo de cada página manualmente com `SidebarProvider` + `Sidebar`.
- **Prós**: Sem route group.
- **Contras**: ~11 edições repetidas, risco alto de perder os `data-tour` e de duplicar lógica; state não persiste sem um provider comum no topo.
- **Por que rejeitada**: alto custo/manutenção; única fonte de verdade da navegação fica pulverizada.

### Alternativa 3: Layout por subpasta (sem route group)

- **Descrição**: Criar `app/(...)` específicos por módulo.
- **Contras**: Duplicaria o shell para cada módulo.
- **Por que rejeitada**: redundância.

## Consequências

### Positivas

- Um único local define o shell (manutenção central).
- Estado de collapse persiste entre páginas do grupo.
- URLs e middleware inalterados.

### Negativas

- Movimentação de arquivos das páginas para `app/(dashboard)/` (mecânica, sem mudança de rota).

### Riscos

- Garrafamento do build devido a muitas páginas em um grupo — não é risco real sem server components pesados no shell.
- Regressão por apontar imports (caminhos `@/` relativos preservados — move os arquivos mantendo imports, que usam alias `@/`).

## Notas de Implementação

- `app/(dashboard)/layout.tsx` → `export default function DashboardLayout({children})` retorna `SidebarProvider > AppSidebar > SidebarInset > Header + children`.
- Mover: `app/page.tsx`, `app/cases/`, `app/clients/`, `app/contracts/`, `app/negotiations/`, `app/agents/`, `app/policies/`, `app/settings/`, `app/admin/` para `app/(dashboard)/`.
- `app/login/`, `app/api/`, `app/loading.tsx` e `app/not-found.tsx` permanecem fora.
- O `Header` atualmente possui `navLinks` — mover essa lista para o config usado pelo `AppSidebar`.
