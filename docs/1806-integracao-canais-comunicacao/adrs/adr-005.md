# ADR-005: Webhook do Telegram autenticado por secret_token por tenant

## Status

Accepted

## Data

2026-08-18

## Contexto

Com um bot por tenant (ADR-003), o endpoint `POST /api/webhook/telegram` receberá eventos de vários bots. Hoje a autenticação usa um único `WEBHOOK_SECRET` global (header `X-Telegram-Bot-Api-Secret-Token`), e o tenant é resolvido depois via `resolveWebhookTenant` buscando o token do bot em `profiles` — frágil e inadequado para multi-bot. É preciso autenticar a origem do evento **e** identificar o tenant dono do bot de forma atômica.

## Decisão

- Ao salvar a configuração do canal Telegram de um tenant, o sistema gera um `webhook_secret` aleatório (padrão de caracteres aceito pela Bot API: `A-Z a-z 0-9 _ -`), cifra e armazena em `channel_configs`.
- O registro automático do webhook (`setWebhook`) envia esse `secret_token`; o Telegram o devolve no header `X-Telegram-Bot-Api-Secret-Token` de cada evento.
- O handler do webhook valida o header contra `channel_configs` (lookup por secret cifrado → comparar hash): uma única consulta autentica a origem, identifica o tenant e o canal, e garante que o canal está habilitado.
- Cada tenant passa a ter o próprio webhook **secreto**; `WEBHOOK_SECRET` global permanece como fallback de demo/desenvolvimento (bot global via `TELEGRAM_BOT_TOKEN` de env) durante a transição.

## Alternativas Consideradas

### Alternativa 1: Path secreto na URL (/api/webhook/telegram/[token])

- **Descrição**: rota dinâmica com segmento de token por tenant.
- **Pros**: sem lookup por header.
- **Cons**: token aparece em URLs, logs de proxy e potencialmente em referências; exige rota dinâmica nova; segredo em URL é anti-padrão.
- **Why rejected**: o header de secret_token da Bot API resolve o mesmo problema sem vazar o segredo.

### Alternativa 2: Secret global único + resolução de tenant via getMe

- **Descrição**: manter `WEBHOOK_SECRET` global e, a cada evento, chamar `getMe` com o token de cada config para identificar o bot.
- **Cons**: N chamadas à API do Telegram por evento (ou manutenção de cache bot_id→tenant); secret compartilhado não distingue tenants; degrada com o número de tenants.
- **Why rejected**: custo por evento e fragilidade; o secret por tenant elimina ambos.

## Consequências

### Positivas

- Autenticação de origem + resolução de tenant em uma consulta só, índice único no secret.
- Impossível enviar eventos forjados de um tenant para outro sem o secret do respectivo bot.

### Negativas

- Lookup por valor cifrado não é indexável diretamente: armazenar também um **hash** determinístico do secret (SHA-256) em coluna indexada para o lookup, mantendo o secret cifrado para o registro do webhook.
- Migração: bots já registrados com o secret global precisam ter o webhook re-registrado com o novo secret (ação do registro automático ao salvar a config).

### Riscos

- Rotacao/perda do secret exige re-registro do webhook — coberto pela mesma ação de salvar config.

## Notas de Implementação

- `channel_configs.webhook_secret_hash` (único, indexado) + `webhook_secret_enc` (cifrado).
- O WhatsApp (Z-API) continua validando `X-Webhook-Secret` global na transição; a mesma tabela permite migrá-lo depois para secret por tenant.
