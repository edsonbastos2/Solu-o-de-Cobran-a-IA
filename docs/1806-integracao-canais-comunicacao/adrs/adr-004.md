# ADR-004: Módulo `lib/channels/` com interface de canal e registry

## Status

Accepted

## Data

2026-08-18

## Contexto

O projeto organiza toda a lógica de negócio em `lib/` plano (30+ arquivos). A plataforma de canais introduzirá cerca de 6 arquivos coesos (interface, dois adapters, registry, serviço de envio, processamento de inbound). Espalhar isso na raiz de `lib/` junto de `whatsapp.ts`/`telegram.ts` legados criaria confusão entre módulo novo e legado, e o módulo tem fronteira conceitual clara (o domínio depende da interface, nunca dos adapters).

## Decisão

Criar o diretório `lib/channels/` contendo:

- `types.ts` — tipos compartilhados do módulo (`ChannelId`, `OutboundMessage`, `SendResult`, `InboundMessage`, capacidades declaradas por canal).
- `channel.ts` — interface `CommunicationChannel` (`id`, `sendMessage`, `validateRecipient`) e o contrato de capacidades.
- `whatsapp-channel.ts` — adapter Z-API (absorve `lib/whatsapp.ts`).
- `telegram-channel.ts` — adapter Bot API (absorve `lib/telegram.ts`).
- `registry.ts` — registro de canais por `ChannelId` (Strategy Pattern); resolução de canal por tenant lendo a config de canal.
- `message-service.ts` — serviço de envio usado pelo domínio: resolve canal ativo do caso, despacha via interface e persiste resultado.
- `inbound.ts` — processamento unificado de mensagens recebidas (idempotência, resolução de cliente/caso, registro, encaminhamento ao pipeline).

`lib/messaging.ts` permanece como fachada transitória delegando ao `message-service`, até que todos os callers sejam atualizados.

## Alternativas Consideradas

### Alternativa 1: Arquivos planos em lib/

- **Descrição**: seguir o padrão atual com `lib/channel.ts`, `lib/channel-telegram.ts` etc. na raiz.
- **Pros**: uniformidade com o resto do projeto.
- **Cons**: ~6 arquivos novos soltos junto aos legados `whatsapp.ts`/`telegram.ts`; fronteira do módulo invisível; risco de o domínio importar adapter direto.
- **Why rejected**: a coesão do módulo justifica o subdiretório; o path alias `@/lib/channels/...` mantém os imports limpos.

### Alternativa 2: Camada `src/channels/` com Clean Architecture completa (domínio/aplicação/infra)

- **Descrição**: estrutura em camadas com entidades de domínio e ports independentes do Next.js.
- **Pros**: isolamento máximo.
- **Cons**: o projeto não tem camadas (`lib/` é a camada de negócio); introduziria uma arquitetura paralela desproporcional; YAGNI.
- **Why rejected**: incompatível com a arquitetura existente — a separação domínio/adapter já é alcançada pela interface no módulo.

## Consequências

### Positivas

- Fronteira explícita: regra de negócio importa apenas `@/lib/channels/message-service` e tipos; nunca um adapter concreto.
- Legado (`lib/whatsapp.ts`, `lib/telegram.ts`, `lib/messaging.ts`) pode ser removido ao final sem caçar referências.

### Negativas

- Primeiro subdiretório de módulo em `lib/` — precedente a ser aplicado com parcimônia.

## Notas de Implementação

- Interface mínima: `sendMessage`, `validateRecipient`. `receiveMessage`/`getStatus` não entram: recebimento é push de webhook (adapters expõem `parseInboundEvent`), e status é parte do `SendResult`/capacidades declaradas — não forçar interface artificial.
