# ADR-006: Evoluir a tabela `messages` em vez de criar tabela de canal separada

## Status

Accepted

## Data

2026-08-18

## Contexto

O PRD exige histórico rastreável por canal (canal, direção, ID externo, resultado do envio). A tabela `messages` atual (`id, tenant_id, case_id, role ('user'|'ai'|'human'|'system'), content, created_at`) alimenta a UI de conversa do caso e o pipeline de IA. Havia duas opções: evoluir essa tabela ou criar `channel_messages` separada.

## Decisão

Evoluir `public.messages` com colunas novas:

- `channel TEXT` — `whatsapp` | `telegram` | null (mensagens internas do sistema sem canal, ex.: avisos e histórico legado).
- `external_message_id TEXT` — ID da mensagem no provedor quando disponível; único por tenant (`UNIQUE (tenant_id, channel, external_message_id)` com NULLS NOT DISTINCT onde aplicável) para idempotência de eventos de status futuros.
- `send_status TEXT` — `pending` | `sent` | `failed` (mensagens recebidas: `received`).
- `status_error TEXT` — motivo da falha em linguagem clara (nunca payload do erro, que pode conter dados sensíveis).
- `sent_at TIMESTAMPTZ` — timestamp do resultado do envio.

**Direção não vira coluna**: é dedutível de `role` (`user` = entrada; `ai`/`human` = saída; `system` = interna). Adicionar `direction` duplicaria informação já existente.

Status limitados às capacidades reais (ADR-001/PRD): Telegram e WhatsApp nesta fase registram apenas `sent`/`failed`/`received`.

## Alternativas Consideradas

### Alternativa 1: Tabela `channel_messages` separada

- **Descrição**: tabela dedicada ao tráfego de canais, mantendo `messages` intacta.
- **Pros**: zero risco à tabela existente.
- **Cons**: duas fontes de verdade para a mesma conversa; UI do caso precisaria de JOIN/UNION; pipeline de IA lê histórico de `messages` e não veria as mensagens por canal.
- **Why rejected**: a mensagem **é** o mesmo agregado; separar fragmenta o histórico que a IA usa como contexto.

### Alternativa 2: Coluna `direction` além de `role`

- **Descrição**: redundância explícita de direção.
- **Pros**: consulta direta por direção.
- **Cons**: dois campos que precisam concordar sempre; migração de dados históricos ambígua.
- **Why rejected**: derivação de `role` é estável e já usada pela UI.

## Consequências

### Positivas

- UI de conversa e pipeline de IA continuam funcionando sem JOIN; colunas novas são opcionais.
- Índice único `(tenant_id, channel, external_message_id)` prepara idempotência para webhooks de status futuros (fase 2).

### Negativas

- Migration em tabela em produção (ADD COLUMN nullable — seguro).
- Mensagens históricas ficam com `channel` null; a UI deve tratar null como "canal não identificado".

## Notas de Implementação

- `supabase_channel_platform.sql` (migration manual, padrão do projeto): ADD COLUMNs, índices e RLS já coberta pela policy `tenant_isolation` existente (messages está no loop de policies do tenant_model).
- Inserts do pipeline de IA (`lib/agent.ts`) passam a gravar `channel` + `send_status` quando o envio é disparado.
