# ADR-002: Etapas e transições como domínio em código, com tabela dedicada de histórico

## Status

Accepted

## Data

2026-08-25

## Contexto

O CRM precisa de etapas de funil com transições validadas e histórico de movimentação (ADR-001 do PRD). Nesta entrega as etapas são fixas, mas a arquitetura deve permitir configuração por tenant no futuro. O projeto já tem dois mecanismos de registro: `audit_logs` (auditoria com before/after) e `conversation_events` (timeline da conversa).

## Decisão

1. **Etapas, transições permitidas e correspondência etapa↔status vivem em um módulo de domínio em código** (`lib/crm/stages.ts`): tipos `CrmStage`, metadados das etapas (rótulo, ordem, fluxo/exceção), mapa de transições e a função de sincronização com o status atual do caso. API e UI consomem esse módulo — nenhum componente conhece as regras isoladamente. A evolução para etapas por tenant (Fase 2) substituirá a fonte de dados do contrato sem mudar os consumidores.
2. **Histórico de movimentação em tabela dedicada `case_stage_history`** (append-only: caso, tenant, etapa de origem/destino, autor, motivo, data), com RLS espelhando `cases`. Auditoria continua em `audit_logs`; a timeline do chat (`conversation_events`) não é poluída com movimentação de funil.
3. Colunas novas em `cases`: `crm_stage` (default `NOVO`) e `priority` (`alta|media|baixa`, default `media`), com backfill na migração a partir do status atual.

## Alternativas Consideradas

### Alternativa 1: Tabelas crm_stages + crm_stage_transitions seeded por tenant desde já

- **Prós**: Flexibilidade imediata; configuração por tenant pronta.
- **Contras**: Mais escopo (RLS, seeds, API de leitura) para requisito que não existe no MVP; YAGNI.
- **Por que rejeitada**: O contrato de consumo estável (módulo de domínio) permite migrar para tabelas depois sem retrabalho de UI/API.

### Alternativa 2: Histórico em conversation_events (novo tipo CASE_STAGE_CHANGED)

- **Prós**: Menos uma tabela; já tem RLS.
- **Contras**: Acopla o histórico do funil ao ciclo de vida da conversa; polui a timeline do chat com eventos que não são de conversa; consulta para métricas futuras fica enviesada.
- **Por que rejeitada**: O histórico de etapa é dado de domínio do caso, não da conversa.

## Consequências

### Positivas

- Regras de transição e sincronização centralizadas, testáveis em unidade pura.
- Base de dados enxuta: uma coluna, uma tabela de histórico.
- Métricas futuras (tempo por etapa, conversão) têm fonte própria e imutável.

### Negativas

- Adicionar/alterar etapas exige mudança em código até a Fase 2.
- Mais uma migração SQL manual a aplicar (padrão já estabelecido no projeto).

### Riscos

- Divergência entre `crm_stage` e `status` se alguma via de mutação ignorar a sincronização → mitigação: sincronização aplicada apenas na operação de domínio de mudança de etapa (`lib/crm`), validada em testes.

## Notas de Implementação

- Migração: `supabase_crm_board.sql` (colunas + tabela + RLS + índices + backfill).
- Backfill por correspondência: `not_started→NOVO`, `in_negotiation→EM_NEGOCIACAO`, `needs_attention→ESCALADO`, `closed→ENCERRADO`.
