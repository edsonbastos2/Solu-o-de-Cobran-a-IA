# ADR-004: Lazy one-shot migration from profiles AI columns to tenants.settings.ai

## Status

Accepted

## Date

2026-08-10

## Context

The per-user AI config in `profiles` (`ai_provider`, `ai_model`, `opencode_api_key`, `gemini_api_key`, `openai_api_key`, `anthropic_api_key`, `openrouter_api_key`, `ollama_base_url`) is the only existing source of truth. Tenants today have `settings = '{}'`. After this feature, `tenants.settings.ai.assistant` becomes authoritative for the assistant/agents buckets; a migration must populate it without forcing every owner to reconfigure do zero, and without downtime. The `agents` bucket has no per-user analogue, so migration only covers `assistant` (= the existing per-user config: provider, model, keys, ollama base url).

## Decision

Use a **lazy** migration triggered on the first authenticated `GET` of the tenant AI config (the new Settings tab load). The endpoint:

1. Loads `tenants.ai_migrated_at`, the tenant's `owner_user_id`, and the owner's `profiles` row.
2. If `ai_migrated_at IS NULL` and the owner has any non-null AI field on `profiles`:
   a. Decrypt the owner's per-provider keys via the existing `get_user_ai_keys(owner_user_id)` RPC (service role).
   b. Build `settings.ai.assistant = { provider, model, ollama_base_url, <provider>_api_key_enc: ai_encrypt(decrypted_key) }`.
   c. Write `settings.ai.assistant`, set `tenants.ai_migrated_at = now()`, in a single `UPDATE tenants ... WHERE id = $ AND ai_migrated_at IS NULL` (conditional UPDATE keeps it idempotent across concurrent requests).
3. Return the (now populated) tenant AI config.

The `profiles` AI columns are **not** removed or cleared in this PRD — they remain as a historical copy and as the source for messaging (Z-API/Telegram). The resolver (`lib/ai-config.ts`) does **not** read `profiles` AI columns anymore; they are legacy.

## Alternatives Considered

### Alternative 1: Manual "Migrar configuração" button

- **Rejected**: Requires every owner to act; many won't and will file "configurar sumiu" tickets.

### Alternative 2: Background cron job scanning tenants without `ai_migrated_at`

- **Rejected**: Adds scheduling surface for a one-time, idempotent operation. Lazy avoids introducing new runtime infra.

### Alternative 3: Move (clear) the profiles columns during migration

- **Rejected**: Reversible for free if migration turns out wrong. Keep the source intact for one release.

## Consequences

### Positive

- Zero-touch for owners: opening the Settings tab after deploy migrates.
- Idempotent via the conditional `WHERE ai_migrated_at IS NULL` UPDATE; concurrent requests cannot double-migrate.
- `profiles` keeps a safety copy of the original config.

### Negative

- Tenants whose owners never visit Settings remain on the documented "fallback to system default" path, which may differ from their prior per-user config (acceptable per ADR-001, mitigated by super-admin defaults).
- The `agents` and `pdf_extraction` buckets start empty for all tenants; they rely on the bucket-chains fallback (`agents` → `assistant`; `pdf_extraction` → system → hardcoded).

## Risks

- A tenant whose owner has no `profiles` AI config gets `ai_migrated_at` stamped on an empty `assistant` bucket — this would lock it out of falling back to the system default. Mitigation: only stamp `ai_migrated_at` if at least one AI field is non-null on `profiles`; otherwise leave `ai_migrated_at NULL` so the bucket stays absent and the chain falls through to system/hardcoded.
- Owner rotated keys in `profiles` after migration: the resolver no longer reads `profiles`, so the tenant's bucket becomes stale. Mitigation: the new Settings tab is the only edit surface after migration; document this clearly in the UI banner.

## Implementation Notes

- New column: `ALTER TABLE public.tenants ADD COLUMN IF NOT EXISTS ai_migrated_at TIMESTAMPTZ;`
- The migration step runs **inside** `GET /api/tenants/[id]/ai-config`, before returning config. It uses the admin client and is service-role only via `requireTenantContext` + `requireRole('admin')`.
