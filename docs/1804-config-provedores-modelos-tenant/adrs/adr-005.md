# ADR-005: Authenticate and tenant-scope /api/debtors/extract-pdf

## Status

Accepted

## Date

2026-08-10

## Context

`app/api/debtors/extract-pdf/route.ts` is currently unauthenticated — it calls no `requireUser`, relies only on `process.env.OPENCODE_API_KEY`, and is excluded from middleware auth by the `/api/extract-contract/*` and `/api/cron/*`-style carve-outs. The PRD requirement that PDF extraction be per-tenant means this route must resolve the tenant AI config (`pdf_extraction` bucket) and therefore must know which tenant is calling. Leaving it unauthenticated would let any caller consume the (now per-tenant) configured key without a session.

## Decision

- Add `requireUser(req)` + `requireTenantContext(req)` at the top of the route, matching the already-authenticated `/api/extract-contract/route.ts` pattern (which already calls `requireUser`).
- Resolve provider/model/key via `resolveAIConfig({ bucket: 'pdf_extraction', tenantId: ctx.tenantId })` (ADR-003), replacing the hardcoded `minimax-m3` + `process.env.OPENCODE_API_KEY` reads.
- Apply the same rate-limit key as `/api/extract-contract` (10/min per user).
- Audit-log the extraction with `tenantId: ctx.tenantId`, mirroring `/api/extract-contract`.
- Update `middleware.ts` so `/api/debtors/extract-pdf` is **not** in the unauthenticated carve-out list (it isn't listed today; only `/api/extract-contract/*`, `/api/webhook/*`, `/api/cron/*` are). Verify and add it to the authenticated default.

## Alternatives Considered

### Alternative 1: Keep unauthenticated; accept tenant_id in the body

- **Rejected**: Anyone on the internet could call it with any `tenant_id` and consume that tenant's keys. Hard fail on security.

### Alternative 2: Leave on env-key (status quo) and only fix `/api/extract-contract`

- **Rejected**: Does not satisfy "PDF extraction per tenant" for the debtors flow, and leaves a public endpoint consuming paid resources.

## Consequences

### Positive

- Closes an existing security gap (a public endpoint spending paid tokens).
- Both extraction routes now resolve config identically via the resolver.

### Negative

- Any internal/automated caller that invoked `/api/debtors/extract-pdf` without a session breaks. Mitigation: known callers are all in-app and use the authenticated `fetchWithAuth` (see `lib/api.ts`); a quick audit confirms no cron dependency on this route.

## Risks

- A tenant that configures a chat-only provider into `pdf_extraction` (e.g. `opencode`/`deepseek-v4-flash`) — the extraction route's current Anthropic-SDK-over-OpenCode client expects a model able to accept `document` content blocks. Mitigation: enforce a vision-capable whitelist at the `pdf_extraction` write site (server-side validation in the tenant config endpoint) and a server-side runtime guard that falls back to the system/hardcoded `minimax-m3` when the configured model is not vision-capable.

## Implementation Notes

- The Anthropic-SDK-over-OpenCode extraction client (`new Anthropic({ baseURL: OPENCODE_BASE_URL, apiKey })`) currently hardcodes `OPENCODE_BASE_URL = 'https://opencode.ai/zen/go'`. The resolver returns `provider`; when `provider !== 'opencode'`, the extraction route must dispatch to a provider-appropriate client (existing `callLLM` is text-only and cannot accept document blocks). For the MVP, constrain `pdf_extraction` providers to `opencode` and `anthropic` (both reachable via the Anthropic SDK with a base-url switch), and reject the other providers at the tenant config write site with a clear UI message. This keeps the extraction client single-SDK while delivering per-tenant provider+key+model selection over OpenCode/Anthropic.
