# ADR-001: Tenant-scoped AI provider/model configuration with per-function buckets and one-shot migration

## Status

Accepted

## Date

2026-08-10

## Context

The collection platform's AI configuration (provider, model, API keys) currently lives **per-user** in the `profiles` table, resolved at runtime from the case owner's `profiles` row with hardcoded fallbacks and a single implicit system default (`process.env.OPENCODE_API_KEY`). The app has since migrated to a multi-tenant model (`tenants` + `tenant_members`), with a `tenants.settings` JSONB column that no application code reads or writes. There is no concept of super-admin system defaults for AI, and the PDF contract extraction routes (`/api/extract-contract`, `/api/debtors/extract-pdf`) are fully hardcoded to one provider/model (`minimax-m3` via OpenCode) using a global env key.

The product needs each tenant to configure its own AI providers and models for (a) the system collection assistant, (b) PDF data extraction for its collection agents, and (c) the collection-agent pipeline; and a super-admin needs to set provider/model defaults for the whole system.

## Decision

Adopt a **tenant-scoped, per-function-bucket** AI configuration model, delivered as a single MVP, with a clear resolution chain and a one-shot migration from per-user config:

1. **Tenant configuration** is stored in `tenants` (new structured AI settings) and organized into **three buckets**: `assistant` (collection chat + help-chat), `pdf_extraction` (contract/debtor PDF extraction), and `agents` (the multi-agent collection pipeline). Each bucket holds a provider, a model, and per-provider API keys for the six supported providers (opencode, gemini, openai, anthropic, openrouter, ollama).
2. **System defaults** are managed by the super-admin in a new `/admin` page and organized into **two buckets**: `assistant` and `pdf_extraction`. Secrets live encrypted at the system-config level.
3. **Resolution chain** (most specific first):
   - For the agents pipeline: per-agent `model` override (model only, provider always from the tenant `agents` bucket) → tenant `assistant` bucket →
   - System `assistant` default → hardcoded fallback (current behavior).
   - For the system assistant / help-chat: tenant `assistant` bucket → system `assistant` default → hardcoded fallback.
   - For PDF extraction: tenant `pdf_extraction` bucket → system `pdf_extraction` default → hardcoded fallback (existing `minimax-m3`/OpenCode env-key behavior).
4. **Override-per-agent preserved**: each `agents` row keeps its `model` field and continues to override only the model within the agents pipeline; the provider and keys come from the tenant `agents` bucket.
5. **One-shot migration**: on the owner's first visit to the new Settings tenant-tab after deploy, the tenant's existing AI config (provider, model, keys) is copied from the owner's `profiles` row into `tenants.settings` (re-encrypted via the existing `ai_encrypt` RPC). The `profiles` AI columns stop being the source of truth for AI; they may remain for messaging (Z-API/Telegram) settings.
6. **Permissions**: only `owner`/`admin` of a tenant can edit that tenant's AI config; super-admins additionally manage system defaults and may switch tenants via the existing `?tenant_id=` mechanism.
7. **UI placement**: tenant AI config lives in a new "Configurações do Tenant" tab inside `app/(dashboard)/settings`; system defaults live in a new `app/(dashboard)/admin/ai-defaults` page.

## Alternatives Considered

### Alternative 1: Phased MVP (assistant first, PDF extraction later) — Approach B rejected

- **Description**: Phase 1 ships only the `assistant` + `agents` buckets for tenants and the `assistant` system default; PDF extraction remains hardcoded until Phase 2.
- **Pros**: Smaller first deployment; isolates risk of breaking PDF extraction.
- **Cons**: Leaves the explicit "PDF extraction per tenant" product ask unfulfilled for one phase; users ask why extraction isn't configurable; two passes over the extraction routes.

### Alternative 2: Assistant-only MVP — Approach C rejected

- **Description**: MVP ships only the `assistant` bucket per tenant + system default; extraction and agents stay hardcoded.
- **Pros**: Smallest possible surface.
- **Cons**: Fails to meet the explicitly requested per-tenant PDF extraction and per-tenant agent capabilities; defers most of the product value.

### Alternative 3: Keep per-user `profiles` as a personal fallback below tenant

- **Description**: Add tenant config but keep `profiles` AI columns as a lowest-priority personal fallback, edited in the existing Settings "IA" tab.
- **Pros**: Lets a user keep personal preferences; no forced migration.
- **Cons**: Creates ambiguity about which config is authoritative; complicates the resolution chain; leaks a tenant's chosen keys into a personal space; not what the product asked for.

## Consequences

### Positive

- Tenants self-serve AI configuration per function without super-admin involvement.
- Super-admins get a runtime UI for system defaults, eliminating redeploys to change the global default provider/model.
- The two PDF extraction routes become tenant-scoped and authenticated, closing the `/api/debtors/extract-pdf` unauthenticated gap as a side effect.
- A single transparent resolution chain replaces scattered hardcoded ternaries and env-key fallbacks across 6+ files.

### Negative

- Larger first MVP: touches Settings UI, a new admin page, two extraction routes, ~7 resolution call sites, schema additions and a migration; no phased safety net for PDF extraction.
- Requires re-encrypting keys from `profiles` into tenant-level storage during one-shot migration; the migration is idempotent and reversible but must run once per owner.
- The `agents` table does not gain a `provider` column (intentional, to bound scope); per-agent provider override is a deferred Non-Goal.

### Risks

- **Migration correctness**: a faulty one-shot migration could lose tenant keys. Mitigation: copy (not move) during migration, leave `profiles` AI columns intact for one release, and gate migration on a `migrated_at` flag to prevent re-runs.
- **Extraction route hardening**: authenticating and tenant-scoping `/api/debtors/extract-pdf` changes behavior; existing callers must send a valid session. Mitigation: validate against the authenticated user's active tenant before the cut-over.
- **Resolution ambiguity**: with three sources (agent override, tenant bucket, system default), a wrong precedence can route billing to the wrong key. Mitigation: centralize resolution in one server helper with explicit precedence and unit-test it.

## Implementation Notes

- New structured AI settings live on `tenants` (extend the existing `settings JSONB` or add a dedicated child table; the TechSpec decides). System defaults live on a new super-admin-only row/table.
- Secrets at both the tenant and system level reuse the existing `ai_encrypt`/`ai_decrypt` Vault-backed RPC (`supabase_ai_keys_encryption.sql`); service-role access only.
- A single server-side resolver (e.g. `lib/ai-config.ts`) replaces the per-file ternaries and `OPENCODE_API_KEY` env fallbacks in `lib/agent.ts`, `lib/case-insights.ts`, `app/api/start-negotiation/route.ts`, `app/api/help-chat/route.ts`, `app/api/extract-contract/route.ts`, and `app/api/debtors/extract-pdf/route.ts`.
- `process.env.OPENCODE_API_KEY` remains only as the final hardcoded fallback in the resolver, not scattered.
