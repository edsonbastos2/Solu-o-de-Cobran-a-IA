# ADR-003: Single AI config resolver (lib/ai-config.ts) with per-function resolution chains

## Status

Accepted

## Date

2026-08-10

## Context

Today the provider + model + key resolution is duplicated across six call sites (`lib/agent.ts`, `lib/case-insights.ts`, `app/api/start-negotiation/route.ts`, `app/api/help-chat/route.ts`, `app/api/extract-contract/route.ts`, `app/api/debtors/extract-pdf/route.ts`), each with its own ternary over `profiles.ai_provider`/`ai_model` and its own `process.env.<PROVIDER>_API_KEY` fallback, including the hardcoded `minimax-m3`/OpenCode in the two extraction routes. With tenant + system config introduced, every site must consult two more levels (tenant bucket, system default) before the hardcoded fallback. Scattering this across six files guarantees drift and wrong billing targets.

## Decision

Introduce a single server-side resolver module `lib/ai-config.ts` exposing `resolveAIConfig(...)`. Call sites invoke it **once per request** and reuse the result across all LLM calls the request makes (notably the multi-agent pipeline, which sends several LLM calls per case message). The resolver returns a normalized `{ provider, model, apiKey, ollamaBaseUrl, source }` where `source` enumerates which level won (`tenant.<bucket>` | `system.<bucket>` | `hardcoded`) for UI diagnostics.

### Resolution chains

- **assistant** (chat de cobrança `processChat`, help-chat): `tenant.ai.assistant` → `system_ai_defaults['assistant']` → hardcoded (`opencode` / `deepseek-v4-flash` / `process.env.OPENCODE_API_KEY`).
- **pdf_extraction** (`extract-contract`, `debtors/extract-pdf`): `tenant.ai.pdf_extraction` → `system_ai_defaults['pdf_extraction']` → hardcoded (`opencode` / `minimax-m3` / `process.env.OPENCODE_API_KEY`).
- **agents** (`processChat` multi-agent pipeline): per-agent `agents.model` overrides only the model; the provider + keys always come from the bucket chain `tenant.ai.agents` → `tenant.ai.assistant` → `system_ai_defaults['assistant']` → hardcoded. The agent-row `model` (string) overrides the model within this chain.

The fallback to `*.<assistant>` inside the agents chain means a tenant that configures only the assistant bucket gets a coherent agents pipeline without configuring a separate bucket.

### Secrets

Secrets are decrypted once per request inside the resolver via the service-role RPC `get_tenant_ai_keys` (tenant) and a `get_system_ai_keys` (system) — never returned to the client.

## Alternatives Considered

### Alternative 1: Resolve per LLM call (no per-request memoization)

- **Pros**: Trivially stateless.
- **Cons**: Each multi-agent message (3+ LLM calls) re-runs 2 Supabase queries per call — wasted round-trips on a path where LLM latency already dominates.

### Alternative 2: In-process TTL cache (Map keyed by tenant+bucket, ~30s)

- **Pros**: Fewer queries under concurrency.
- **Cons**: Introduces invalidation concerns when an owner edits config (stale until TTL). Config writes are infrequent and LLM calls cheap to wait, so the added state is not justified.

### Alternative 3: Keep per-file ternaries and extend each with two extra lookups

- **Rejected**: Guaranteed drift; exactly the anti-pattern this resolver removes.

## Consequences

### Positive

- One place to evolve precedence (e.g. add per-agent provider in Phase 2, add budget caps in Phase 2).
- Diagnostics: the `source` field lets the UI say "usando configuração do tenant" vs "usando padrão de sistema" vs "fallback" without a separate audit.
- Removes the scattered `process.env.<PROVIDER>_API_KEY` fallbacks; `lib/ai-config.ts` becomes the only reader of those env vars.

### Negative

- Six files are touched at once; risk of behaviour drift during the cut-over.
- The agents chain matches `tenant.ai.assistant` as a second resort, so a tenant that intentionally leaves `agents` empty but sets `assistant` to a low-context model gets that model for agents too (semantically reasonable: agents fall back to the assistant's choice).

## Risks

- **Precedence bugs** can bill the wrong key. Mitigation: centralized helper, unit-tested chains for each bucket with/without each level set.
- **Extraction route semantics** for `minimax-m3` differ from chat models; if a tenant picks a chat-only model into `pdf_extraction`, the Anthropic-SDK-over-OpenCode extraction call may behave differently. Mitigation: validate the `pdf_extraction` provider/model against a vision-capable whitelist at write time, with a server-side guard.

## Implementation Notes

- Resolver signature (illustrative):
  ```ts
  export type AIBucket = 'assistant' | 'pdf_extraction' | 'agents';
  export interface AIResolved { provider: string; model: string; apiKey: string; ollamaBaseUrl: string; source: 'tenant' | 'system' | 'hardcoded'; }
  export async function resolveAIConfig(opts: {
    adminClient: SupabaseClient; tenantId: UUID; bucket: AIBucket;
    agentModelOverride?: string; // applies to 'agents' bucket only
  }): Promise<AIResolved>;
  ```
- Replace the ternaries and `OPENCODE_API_KEY`/`GEMINI_API_KEY`/etc. env reads at the six call sites with a single `resolveAIConfig` call at request start.
