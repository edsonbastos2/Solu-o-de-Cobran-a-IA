# ADR-002: Tenant AI config in tenants.settings JSONB; system defaults in a dedicated table

## Status

Accepted

## Date

2026-08-10

## Context

The feature stores AI configuration (provider, model, per-provider API keys) at two scopes:
- Per tenant, organized into three buckets: `assistant`, `pdf_extraction`, `agents`.
- Per system (super-admin), organized into two buckets: `assistant`, `pdf_extraction`.

The existing `tenants` table already has a `settings JSONB` column that no application code uses. The existing per-user config lives in `profiles` columns, encrypted via the `ai_encrypt`/`ai_decrypt` Vault-backed RPC (`supabase_ai_keys_encryption.sql`), with `get_user_ai_keys(p_user_id)` returning decrypted secrets to service role only.

## Decision

- **Per-tenant AI config**: extend the existing `tenants.settings` JSONB. Store config under a top-level `ai` object with one key per bucket (`assistant`, `pdf_extraction`, `agents`). Each bucket holds `provider`, `model`, and the matching provider secret (`*_api_key_enc`) **pre-encrypted by the `ai_encrypt` RPC before write** — secrets never travel to the DB in plaintext at rest, consistent with the current `profiles` approach. Non-secret bucket metadata can be read directly; secrets are decrypted only server-side through `ai_decrypt`.
- **System defaults**: create a new table `public.system_ai_defaults` with one row per bucket, accessed **only** via service role (admin client). PK on `bucket`, columns for `provider`, `model`, and the per-provider `*_api_key_enc` (encrypted the same way). RLS disabled / access restricted to service role via `GRANT` only.
- **Reading secrets**: a new service-role RPC `get_tenant_ai_keys(p_tenant_id)` mirrors `get_user_ai_keys` and decrypts the active bucket's secret at the same level; the resolver calls it once per request.

## Alternatives Considered

### Alternative 1: Dedicated `tenant_ai_configs` table (one row per bucket) with FK + RLS

- **Description**: Strongly typed columns, FK to tenants, RLS via `can_access_tenant`.
- **Pros**: Query-friendly, typed columns, native FK integrity.
- **Cons**: New table, new RLS policies, more migration surface; the existing `tenants.settings` JSONB remains unused. Overkill for three buckets.

### Alternative 2: JSONB config + separate encrypted column for secrets on tenants

- **Description**: Non-secret config (bucket→provider/model) in `tenants.settings`; secrets in a separate `tenants.ai_secrets JSONB`.
- **Pros**: Clean separation of public config from secrets.
- **Cons**: Two write paths to keep in sync; mixed JSONB cells add complexity without real benefit since both still live on the same row.

### Alternative 3: Store system defaults on the super-admin's `profiles` row

- **Rejected**: Which user counts as "the" super-admin is unstable and there can be more than one; defaults would belong to the system, not a person.

## Consequences

### Positive

- Reuses the existing `tenants.settings` JSONB column (no schema renames) and the existing `ai_encrypt`/`ai_decrypt`/Vault infrastructure.
- System defaults sit in a tiny dedicated table with native PK on `bucket` — easy to query, easy to grant service-role-only.
- A symmetric RPC `get_tenant_ai_keys` keeps the secret-decryption boundary server-side and consistent with `get_user_ai_keys`.

### Negative

- Loose typing inside JSONB (must validate provider/model in app code and via a small `CHECK` constraint or validator).
- Two storage primitives (JSONB on tenants + dedicated table for system) — slightly more to reason about.

## Negative Risks (shared with ADR-003)

- A tenant could grow per-bucket arrays of historical keys — out of scope; only the active bucket is kept.
- Decryption RPC grows from 1 function to 2 — minor maintenance cost.

## Implementation Notes

- Migration: `ALTER TABLE public.tenants ADD COLUMN IF NOT EXISTS ai_migrated_at TIMESTAMPTZ;` plus the new `system_ai_defaults` table and the `get_tenant_ai_keys` RPC. Document the new env-free behavior in `.env.example`.
- Schema for `system_ai_defaults`:
  ```sql
  CREATE TABLE IF NOT EXISTS public.system_ai_defaults (
    bucket TEXT PRIMARY KEY,                       -- 'assistant' | 'pdf_extraction'
    provider TEXT NOT NULL DEFAULT 'opencode',
    model TEXT NOT NULL DEFAULT 'deepseek-v4-flash',
    opencode_api_key TEXT,
    gemini_api_key TEXT,
    openai_api_key TEXT,
    anthropic_api_key TEXT,
    openrouter_api_key TEXT,
    ollama_base_url TEXT DEFAULT 'http://localhost:11434',
    updated_by UUID REFERENCES auth.users(id) ON DELETE SET NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
  );
  REVOKE ALL ON public.system_ai_defaults FROM anon, authenticated;
  GRANT SELECT, INSERT, UPDATE, DELETE ON public.system_ai_defaults TO service_role;
  ```
