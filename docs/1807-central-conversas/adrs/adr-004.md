# ADR-004: Introdução do Vitest + React Testing Library com testes co-localizados

## Status

Accepted

## Data

2026-08-19

## Contexto

O projeto não possui suite de testes automatizados — validação atual é `npm run lint` + `npm run build` + checklist manual. O PRD da Central de Conversas exige testes dos componentes e fluxos principais (lista, filtros, chat, takeover, transferência, composer), e a extração do chat monolítico da página de caso precisa de rede de segurança contra regressão. O prompt.md especifica Vitest + React Testing Library.

## Decisão

Adotar **Vitest + React Testing Library + jsdom** como primeira infraestrutura de testes do projeto:

- `vitest.config.ts` com `@vitejs/plugin-react`, alias `@/*` e ambiente `jsdom`.
- Dependências de dev: `vitest`, `@vitejs/plugin-react`, `@testing-library/react`, `@testing-library/user-event`, `@testing-library/jest-dom`, `jsdom`.
- Testes **co-localizados** com os arquivos (`components/conversations/*.test.tsx`, `hooks/*.test.ts`), sem pasta `__tests__/` centralizada.
- Scripts: `npm test` (run) e `npm run test:watch`.
- Foco: componentes da Central (renderização, filtros, diferenciação de remetente, estados de loading/erro/vazio, composer com Enter/Shift+Enter/disabled) e lógica de domínio (transições de condutor, derivação de permissões, concorrência por versão) com mocks do Supabase/SWR.

## Alternativas Consideradas

### Alternativa 1: Jest + RTL

- **Pros**: ecossistema maduro, documentação vasta.
- **Cons**: configuração mais pesada para Next.js 15/React 19 (transformadores ESM), runner mais lento; Vitest já é o padrão de facto para Vite/Next modernos.
- **Why rejected**: Vitest oferece a mesma API com setup menor e execução mais rápida.

### Alternativa 2: Pasta `__tests__/` centralizada

- **Pros**: separação estrita de código e teste.
- **Cons**: distância entre teste e componente dificulta manutenção em projeto sem cultura de testes.
- **Why rejected**: co-localização reduz fricção e mantém os testes visíveis junto ao código que cobrem.

## Consequências

### Positivas

- Rede de segurança para a refatoração do chat monolítico.
- Base de testes estabelecida para o restante do projeto.
- Execução rápida integrada ao fluxo de desenvolvimento.

### Negativas

- Nova dependência de dev e mais um comando de verificação (lint + build + test) no fechamento.

### Riscos

- Testes de componentes com SWR/Supabase realtime exigem mocks cuidadosos. Mitigação: mockar `lib/api` (fetcher) e o cliente Supabase na borda, testando componentes como funções puras de props/estado.
